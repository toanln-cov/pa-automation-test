Overview
  • You fill an Excel template, upload it on Configure, the tool applies every row to the Palo Alto firewalls in the Device-ip column through the PAN-OS REST API.
  • What the tool does:
    • Create: tags, address objects, address groups (static), service objects, service groups, security rules, NAT rules.
    • Edit: tags, address objects, address groups, service objects, service groups, security rules, NAT rules.
    • No delete: deleting can have a large impact, so delete by hand on the firewall.
  • Running and finished jobs are in Job history.
  • Configuration jobs write to the candidate config only and never commit on the firewall, to keep the impact as low as possible. The admin reviews, then runs a commit check and a commit on the separate Commit tab.
  • The tool runs one job at a time.
  • No Panorama: the tool does not configure Panorama and does not support firewalls managed by Panorama, to avoid configuration conflicts.
  • PAN-OS versions: only the versions still supported on the Palo Alto PAN-OS API portal (11.1 and later, 10.2, 10.1).

Execution order
  1. Check the file — sheet names and column names must match the template, otherwise the file is refused.
  2. Login — one API key per firewall for the whole job. A firewall with a wrong password or not reachable is skipped, the rows of the other firewalls still run. Every firewall failing → refused before the job is created.
  3. One firewall after the other, each in this order: Read the firewall version to map the API version → Config lock → Backup of the configuration (snapshot Auto-<date time>.xml) → Configure every row of the file → Release the config lock → next firewall.
  4. Order of the rows: the tool runs them one by one, from top to bottom.
  5. The config is always unlocked at the last step, even when the deploy fails.

Config lock: while the job runs, the tool locks the configuration of the firewall so that no other admin changes it at the same time, and releases the lock when that firewall is done. A firewall locked by another admin → nothing is written to it, the job result says so.

Template & sheets

Use one single template file.

template.xlsx
Run orderSheets (always in this order, whatever their order in the file)
1. Add sheetsadd_tag → add_address_object → add_address_group → add_service_object → add_service_group → add_security_rule → add_nat_rule
2. Edit sheetsedit_tag → edit_address_object → edit_address_group → edit_service_object → edit_service_group → edit_security_rule → edit_nat_rule

Note:

  • The import file contains only the sheets you need. Delete every other sheet from the file (an empty sheet left in the file → the whole file is refused). Example: add an address and put it in an existing rule → the file has only add_address_object and edit_security_rule.
  • Inside a sheet, the tool configures the rows one by one from top to bottom, in the order you put them.
  • Several vsys of the same firewall can be configured (shared included).
  • Header colour: red = required, yellow = required in some cases, green = optional.
  • Row 2 of every sheet is an example row: replace it or delete it before the upload.
  • Plain values only, no Excel formula. A cell with invisible characters or an Excel error is refused with its position.
  • Lists are comma separated, without an extra comma or a repeated name.
  • Edit sheets: the tool reads the current configuration on the firewall and changes only what the file fills; everything else is kept. No rename, no move to another vsys.
  • Edit object sheets (edit_tag, edit_address_object, edit_service_object): the tool replaces the whole value with the new one (no Edit-*-mode column), empty cell = kept, none = clear.
  • Edit rule and group sheets: every column has its mode column Edit-<Column>-mode: add (add to the list), remove (remove from the list), replace (new value / full list, none = clear), remain or empty (kept). Details in each sheet.

Shared (object, group, service, tag sheets): Vsys = shared puts the object in shared, where every vsys of the firewall can use it. Notes:

  • A shared group / the tags of a shared object can only use shared objects / tags.
  • A rule is always in a vsys: shared on a rule sheet → the file is refused.
  • A vsys object cannot have the name of a shared object (... already exists in shared); same value → Warning: Duplicate Value with X (shared).
  • Edit sheets edit shared entries too (Vsys = shared).

Dry-run

Dry-run only gets information from the firewall, writes nothing, and reports the result of every row in advance: CAN CREATE / CAN EDIT / CAN MOVE or an error. It checks that the values of the admin's file have the right format and can really be configured on the firewall.

The Dry-run covers most cases before the Install, but not 100% (e.g. interfaces and source users are not checked).

So always run a Dry-run first to reduce input errors. The admin then reviews the result and runs the Install.

Stop duplicated

Stop duplicated (Install only) avoids creating a new object / rule with the same value as an old object / rule already on the firewall. Its only purpose is to create fewer useless objects / rules.

  • Ticked: a row with a duplicate value is skipped, not created. The other rows run as usual.
  • Not ticked: the duplicate row is still created, with a duplicate warning in the result.

The Dry-run always checks these duplicate values and warns about objects / rules that have the same value as the ones to create.

Commit check & Commit

Purpose: template jobs only write to the candidate config and never commit. After a job, an administrator reviews the result and the configuration on the firewall, then decides to run a commit check or a commit. Changes take effect only under the control and approval of an administrator, which reduces the risk of applying a wrong configuration.

Done on the Commit page, separate from the templates. Enter firewall IPs (single, range a-b, CIDR), username and password.

  • Commit check: validate only, nothing applied. Run it first and review the result per firewall.
  • Commit: apply the candidate config.
  • Scope, for both Commit check and Commit (must be chosen, no default): changes of this user only (partial) or all changes.
  • Up to 5 firewalls in parallel. Firewalls without pending changes are skipped.
